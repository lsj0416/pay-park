# 이번달페이 Figma 변경사항 구현 프롬프트

아래 내용을 그대로 Codex에 전달해 작업해줘.

## 작업 목표

`pay-park` 프로젝트에 최신 Figma의 `유경` 페이지 변경사항을 반영해줘.  
현재 모바일 중심 UI를 기준으로 모바일·태블릿·데스크톱 3단계 반응형을 지원해야 한다.

- GitHub 저장소: https://github.com/lsj0416/pay-park
- Figma 파일: https://www.figma.com/design/9cKrTarHBlS8HlDRF0YZke?node-id=79-2
- 기준 페이지: `유경`
- 주요 Figma 레이어
  - `결과`: `79:367`
  - `홈화면`: `79:953`
  - `이거 사도 돼?-1` — 사도 돼요: `165:429`
  - `이거 사도 돼?-2` — 조금 위험해요: `165:31`
  - `이거 사도 돼?-3` — 예산 초과예요: `178:135`

## 작업 전 필수 확인

1. 먼저 저장소 구조, 사용 중인 프레임워크, 라우팅, 상태 관리, 스타일링 방식, 테스트 환경을 확인한다.
2. 관련 화면과 컴포넌트가 어디에 구현되어 있는지 찾고 기존 코드 패턴을 유지한다.
3. Figma를 확인할 수 있다면 위 노드의 디자인과 간격, 색상, 타이포그래피를 우선 기준으로 삼는다.
4. 기존 디자인 토큰이나 공통 컴포넌트가 있으면 재사용하고, 동일 역할의 컴포넌트를 중복 생성하지 않는다.
5. 기존 기능과 사용자의 로컬 저장 데이터를 깨뜨리지 않는다.

## 우선순위 1 — 기능 위치 분리

### 가용 자금 결과 페이지

- 결과 페이지에는 `AI와 활용 계획 세우기` 또는 현재 디자인에 대응하는 AI 계획 CTA만 유지한다.
- CTA를 누르면 기존 `AI 활용 계획` 흐름 또는 화면으로 이동해야 한다.
- 결과 페이지에서 `이거 사도 돼?` 기능, 카드, 버튼, 모달 진입 요소는 제거한다.
- AI 활용 계획과 구매 가능 여부 확인은 서로 완전히 다른 기능으로 취급한다.

### 홈 화면

- `이거 사도 돼?` 진입 요소는 홈 화면에만 둔다.
- 카드 제목은 Figma와 동일하게 `오늘 이거 사도 돼?`를 사용한다.
- 보조 문구는 `결제 전, 지금 예산으로 괜찮은지 바로 확인해요`를 사용한다.
- 단순 정보 카드로 오해하지 않도록 연한 브랜드 컬러 배경, 브랜드 컬러 테두리·제목·화살표를 적용한다.
- 홈의 핵심 가용 자금 카드보다 더 강하게 보이지 않도록 진한 단색 배경은 피한다.
- 카드 전체가 클릭 가능한 버튼 역할을 해야 하며 클릭하면 구매 가능 여부 확인 모달을 연다.

## 우선순위 2 — 구매 가능 여부 판정 로직

판정은 아래 순서대로 수행한다. 조건의 순서를 바꾸지 않는다.

```ts
if (paymentAmount > availableFunds) {
  return 'OVER_BUDGET';
}

if (paymentAmount <= dailyBudget) {
  return 'SAFE';
}

return 'CAUTION';
```

| 상태 | 조건 | 사용자 문구 |
| --- | --- | --- |
| 예산 초과 | `결제액 > 이번 달 가용 자금` | `예산 초과예요` |
| 구매 가능 | `결제액 ≤ 하루 예산` | `사도 돼요` |
| 주의 필요 | `하루 예산 < 결제액 ≤ 가용 자금` | `조금 위험해요` |

경계값도 반드시 위 규칙대로 처리한다.

- `결제액 === 가용 자금`이면 예산 초과가 아니라 `조금 위험해요` 또는 하루 예산 조건에 따른 `사도 돼요`다.
- `결제액 === 하루 예산`이면 `사도 돼요`다.
- 0원, 음수, 숫자가 아닌 값은 계산하지 말고 입력 오류를 표시한다.

계산에 필요한 값은 기존 앱에 저장된 이번 달 가용 자금, 하루 예산, 남은 예산 일수를 사용한다. 동일 계산 유틸리티가 이미 있다면 새로 만들지 말고 재사용한다.

### 공통 계산 기준

```ts
const remainingAfterPayment = availableFunds - paymentAmount;
const adjustedDailyBudget = Math.floor(
  Math.max(0, remainingAfterPayment) / remainingDays
);
```

- `remainingDays`가 0 이하가 되지 않도록 방어한다.
- 금액 표시는 천 단위 콤마와 `원`을 적용한다.
- 음수 금액은 Figma처럼 `−494,130원` 형태로 명확히 표시한다.

### 사도 돼요

- 조건: `결제액 ≤ 하루 예산`
- 상태 제목: `사도 돼요`
- `결제 반영 후 하루 예산`을 보여준다.
- CTA: `결제하고 반영하기`
- CTA를 누르면 기존 예산 반영 로직이 있다면 그대로 연결한다. 없다면 임의의 서버 API를 만들지 말고 현재 프론트엔드 상태·로컬 저장 구조 안에서 반영한다.

### 조금 위험해요

- 조건: `하루 예산 < 결제액 ≤ 가용 자금`
- 상태 제목: `조금 위험해요`
- 결제 후 줄어든 하루 예산을 보여준다.
- 초과 사용분을 여러 날에 나눠 흡수하는 안내를 표시한다.

```ts
const excessAmount = paymentAmount - dailyBudget;
const absorptionDays = Math.max(1, Math.min(5, remainingDays));
const savingPerDay = Math.ceil(excessAmount / absorptionDays);
```

안내 문구 형식:

```text
다음 N일 하루 X원씩 아끼면 나눠서 흡수돼요.
```

기존 코드에 이미 합의된 N일 계산 정책이 있다면 그 정책을 우선 사용하되, 사용자에게 보이는 문구와 계산값이 일치해야 한다.

### 예산 초과예요

- 조건: `결제액 > 가용 자금`
- 상태 제목: `예산 초과예요`
- 결제 후 이번 달 남는 돈을 음수로 보여준다.
- 현재 가용 자금도 함께 보여준다.
- 초과 금액을 포함해 다음 형식으로 안내한다.

```text
이번 달 가용 자금보다 결제액이 X원 커요. 이 결제는 추천하지 않아요.
```

- CTA: `결제하지 않기`
- CTA를 누르면 결제를 반영하지 않고 모달을 닫거나 입력 단계로 돌아간다.
- Figma 예시는 `맥북 2,000,000원`, 가용 자금 `1,505,870원`, 초과 금액 `494,130원`이다. 예시 값을 코드에 고정하지 말고 실제 입력값으로 계산한다.

## 우선순위 3 — 모달 상호작용

- 홈 카드 클릭 시 모달을 연다.
- 기존 Figma의 입력 화면과 세 가지 결과 화면을 한 흐름으로 연결한다.
- 닫기 버튼, 바깥 영역 클릭, `Escape` 키로 닫을 수 있게 한다.
- 모달이 열리면 배경 스크롤을 막는다.
- 열릴 때 첫 입력 요소로 포커스를 이동하고 닫힐 때 홈 카드로 포커스를 돌려준다.
- 모바일에서는 화면 너비에 맞는 바텀시트 또는 현재 Figma 형태를 유지하고, 태블릿·데스크톱에서는 중앙 정렬 다이얼로그로 표시한다.
- 모달 내부 내용이 작은 화면에서 잘리지 않도록 세로 스크롤을 허용한다.

## 우선순위 4 — 3단계 반응형

기존 프로젝트의 브레이크포인트가 있으면 우선 사용한다. 없다면 아래 기준을 적용한다.

| 구간 | 기준 | 레이아웃 원칙 |
| --- | --- | --- |
| 모바일 | `0~767px` | 기존 모바일 UI 유지, 1열, 화면 좌우 여백 16px |
| 태블릿 | `768~1199px` | 콘텐츠 최대 너비를 제한하고 여백 확대, 가능한 영역은 2열 배치 |
| 데스크톱 | `1200px 이상` | 중앙 정렬된 최대 너비 컨테이너, 대시보드 정보를 2열 이상으로 구성 |

반응형 적용 원칙:

- 모바일 디자인을 단순 확대하지 말고 넓어진 공간을 활용해 정보 위계를 정리한다.
- 홈의 핵심 가용 자금 영역과 보조 정보 영역은 태블릿·데스크톱에서 자연스럽게 분리한다.
- `오늘 이거 사도 돼?` 카드는 모든 화면 크기에서 눈에 띄되 핵심 가용 자금 카드보다 우선순위가 높아지지 않게 한다.
- 태블릿·데스크톱에서도 클릭 영역, 텍스트 줄바꿈, 카드 높이가 어색하지 않아야 한다.
- 최소 클릭 영역은 약 44px을 확보한다.
- 가로 스크롤과 화면 밖으로 잘리는 요소가 없어야 한다.

## 구현 제약

- 이번 작업은 로컬 코드 수정까지만 수행한다.
- 커밋, 푸시, 브랜치 생성, PR 생성, 배포는 하지 않는다.
- 새로운 백엔드 API나 인증 기능을 임의로 추가하지 않는다.
- 패키지 추가는 꼭 필요한 경우에만 하며, 먼저 기존 의존성으로 해결 가능한지 확인한다.
- 관련 없는 코드 포맷팅이나 대규모 리팩터링은 하지 않는다.
- 기존 타입, 컴포넌트, 디자인 토큰, 상태 관리 방식을 최대한 재사용한다.

## 검증 항목

작업 후 아래를 직접 확인한다.

1. 결과 페이지에는 AI 활용 계획 CTA만 있고 구매 확인 진입 요소가 없다.
2. 구매 확인 카드는 홈에만 존재하고 클릭 시 모달이 열린다.
3. 세 가지 판정과 두 경계값이 정확하다.
   - `결제액 > 가용 자금` → 예산 초과
   - `결제액 === 가용 자금` → 예산 초과 아님
   - `결제액 === 하루 예산` → 사도 돼요
   - `하루 예산 < 결제액 < 가용 자금` → 조금 위험해요
4. 결제 후 남는 돈, 조정된 하루 예산, 절약 일수·금액이 실제 입력값으로 계산된다.
5. 375px 모바일, 768px 태블릿, 1440px 데스크톱에서 레이아웃을 확인한다.
6. 모달 키보드 조작, 포커스 복귀, 배경 스크롤 차단을 확인한다.
7. 가능한 범위에서 lint, type-check, test, build를 실행한다.
8. 기존 기능에 회귀 문제가 없는지 확인한다.
